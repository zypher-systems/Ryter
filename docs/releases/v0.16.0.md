Two rows on the hat rack. Plan and build are the hats you work in; below a line sit the specialists: an audit hat that runs everything and changes nothing, and a scribe that writes documentation only. The approved plan and the latest audit live at fixed paths every hat knows.

## Upgrade

```sh
ryter update
```

From 0.8.2 or earlier, run the install script once:

```sh
curl -fsSL https://raw.githubusercontent.com/zypher-systems/ryter/main/install.sh | sh
```

Coming from 0.15.0, these behave differently:

- **`Tab` moves within a row, `Shift+Tab` between rows.** In the primary row Tab toggles plan and build. Shift+Tab goes to the specialist you last wore, audit to begin with, and back to the primary you last wore. Tab in the specialist row goes audit, scribe, audit.
- **The review hat is the audit hat.** Everything that said review still loads: sessions, spend records, event logs, `[review]` in `hats.toml`, `[specialists.review]` and `start_hat = "review"` in config. `/review` is `/audit` and says so. The review limit is `audit_usd`; `review_usd` is read as that.
- **The audit hat runs things.** It had review's gate; it has the build hat's now, behind a checkpoint. It may run the project's tests, its end-to-end suite, start the product through the run file, `curl` it, whatever the checks need. Git stays read-only for it.
- **A review is no longer offered after a build turn.** The *offer audits* setting is gone; an old settings file with it loads silently. `/audit` runs one when you want one, with its cost shown first.
- **The hat rack has four blocks** and a separator. The guard card shows the plan file and the audit file.

## What was wrong

- **Switching hats scaled with the number of hats.** Every hat added was one more stop on Tab's way round, and the rack read as one list where two of the entries were the work and the rest were tools.
- **The review hat read but could not try.** Its best evidence was the tests it was allowed to run, and the product itself was out of reach. With the test hat gone there was no hat that could use the product.
- **"Changes nothing" was kept by a list.** The test hat's promise was enforced by reading every command for a write, which three review rounds had to extend and never finished. A promise kept by a list is a promise kept per operating system.
- **A review's result was a message.** You read a verdict in the chat and typed what to do about it. Nothing on disk carried it to the builder or to the next session.
- **The plan and the audit had no fixed address.** Plans were dated files under `.ryter/plans/`; a hat had to be told which one was current.

## What changed

- **Two rows.** Plan and build above a hairline labelled specialists; audit and scribe below. Tab within a row, Shift+Tab between rows, each row remembering its last hat. The bar shows both rows with a dot between; narrow screens fold the row you are not in to a count. `/plan`, `/build`, `/audit`, `/scribe` (or `/docs`) jump straight to a hat.
- **The audit hat.** Reads everything but secrets. Runs what the build hat may run. Before an audit turn Ryter takes a checkpoint, as before a build turn; after it, if the tree moved, Ryter puts it back and records which files, and the audit says so. The audit ends with `file_audit`: a verdict, a summary, the findings worst first, each with where it is, what is wrong and what was seen, and what was run. Ryter writes it to `.ryter/audit.md`, replaced each time, and to `.ryter/audits/<date>-<slug>.md`, kept.
- **The audit card.** The audit opens as a popout over the conversation: the verdict, the findings opened out, what ran, whether the tree changed, where it was written. `y` puts the build hat on and starts a turn whose message is the audit, under "repair what this audit found". `n` closes it, `o` opens the file, the keys and the mouse wheel scroll it. That `y` is your switch; Ryter makes no hat change on its own but one.
- **`/audit` from any hat** runs an audit of the uncommitted work against the plan and brings your hat back when it ends, card open. A plain message in the audit hat is an audit too.
- **The builder reads the audit.** When `.ryter/audit.md` is newer than the plan, the build hat reads it before changing anything and says which findings it addresses.
- **The plan file.** Approving a plan writes `.ryter/plan.md` beside the dated copy. Every hat is told about it: the build works from it, the audit judges against it, the scribe documents it. A resumed session with no plan on record picks it up. The write is the one hat change Ryter makes itself: plan into build, as before.
- **The scribe.** A hat for documentation on a model of its own, cheap if you like. It writes `.md`, `.mdx`, `.txt`, `.rst`, `.adoc`, and `README`, `CHANGELOG`, `LICENSE`, `CONTRIBUTING`, `NOTICE`, `AUTHORS` with no extension, anywhere in the project, and nothing else; the refusal says to press Shift+Tab to build for code. It runs read-only commands. Its block in the rack counts the documents it wrote. It is violet.
- **The rack and the instruments.** Four blocks and the separator, fixed height; the audit block counts verdicts and says whether the last audit changed nothing or restored files; the scribe block counts documents. The guard card names the plan file and the audit file, and says `checkpoint, restored` or `docs only` for the hat that is on.
- **Popouts scroll with the mouse.** The plan panel, the audit card, and every panel that scrolls.

## Tried before release

- **The whole test suite** on Linux: 663 tests pass, with the acceptance suite and both benchmark steps. New tests cover the rows and keys from every hat, the aliases loading, the rack's separator and blocks, the bar's folds, the guard rows, the wheel; the audit tool's shape, its Markdown, both files, the event, the checkpoint taken and the tree restored or left, a folder with no repository, `/audit` from plan and build putting the hat back, `y` starting the repair turn; `plan.md` written and replaced, the pickup on resume, that only approval changes the hat by itself; the scribe's allowed names and refused code, its read-only commands, its seat, its block, `--hat scribe`.
- **In a terminal, against the simulated provider** so no model was paid for: the bar and the rack with four hats; Tab and Shift+Tab across both rows with the last specialist remembered; `/review` saying it is `/audit`; an audit turn filing a failing audit, the card with its findings, the file and its dated copy, `y` putting the build hat on and starting the repair with the audit as the message; a plan approved from its popout writing `plan.md` and the dated copy, the notice naming the file, the switch into build.

### Fixed after review

The release PR's two external reviews found defects in the audit's rollback and the spend figures, over two rounds. Each fix but the last has a test that fails on the reviewed code; the failed-comparison path is hard to force and is covered by reading:

- **A yes given during an audit turn was undone at its end.** A run file or a plan the user approved while the audit ran, or the build hat's edits after a `request_hat` or a plan approval the user said yes to, were restored away with the audit's own changes. Now everything under this session's `.ryter/` is left alone by the rollback, and a yes that puts another hat on, by `request_hat` or by approving a plan, closes the audit there, tree put back and findings filed, before the next hat works. A yes that puts the audit hat on in the middle of a turn starts an audit phase of its own, with its checkpoint.
- **A session started below the repository's top restored the audit's own files away.** Git names changed paths from the top; the exemption now maps them to the session's folder first.
- **Audit and scribe spend was shown as crew mode.** The project spend's hats' share counts audit, review as older records say it, and scribe.
- **A failed after-snapshot dropped the checkpoint in silence.** If the tree cannot be compared after an audit, the whole tree is put back from the checkpoint and the chat says so; a checkpoint that cannot be taken says why and holds the audit to read-only commands.

Also from the reviews: a chord (`Ctrl+Y`) is not one of the audit card's keys; the guide, the system prompt, the `/models` hint and the mid-turn `/audit` notice no longer say three hats or review; `request_hat` names the scribe among the hats.
