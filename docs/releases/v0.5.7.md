The crew builds in the right order. A task waits for the ones it builds on, a new project's scaffold lands before anything else starts, and a builder that's stuck on something only you can fix says so instead of working around it.

## What was wrong

A crew run building a new Rust app spent $2.29, mostly on retries that couldn't pass:

- **The scaffold got stuck.** It needed a system sound library that wasn't installed. The builder spent 80 calls working around it: it tried `sudo`, downloaded packages, and unpacked a copy into `~/.local`. It never said it was stuck.
- **The other three tasks started anyway.** The scaffold was the task that creates `Cargo.toml`. The plan said the other three came after it, but only in prose, and nothing enforced it. So they ran on an empty project, and each was rejected three times because there was no `Cargo.toml` to build.
- **Nothing tested the finished app.** No checks were set, so the combined patch would have landed without anything building it.

## What changed

- **Tasks run in order.** A task can list the tasks it builds on (`after`). It starts only once they have landed, so it builds against their real code. The architect and the lead are told to use it.
- **A new project's scaffold goes first.** When the project has no build manifest yet (`Cargo.toml`, `package.json`, `pyproject.toml`, `go.mod`, …), the task that creates it runs first and alone. Everything else waits for it, whether or not the plan says so.
- **Waiting tasks don't burn money.** If what a task builds on is blocked, the task never starts. The lead gets a single message saying what it waits on and why:

  ```
  - `greet` waits on `scaffold` (blocked: the builder is blocked: To unblock: `sudo dnf install libpq-devel`)
  ```

- **A stuck builder says so.** When something outside its task stops it, such as a missing system package or a module another task hasn't written yet, a builder now stops with `BLOCKED` and says what would fix it. Its work is kept on its branch. It isn't checked or audited, and no retry is spent. The lead tells you what to run. Builders are also told never to use `sudo`, install packages, or write outside their worktree.
- **"Can't verify yet" isn't a failure.** When no checks ran and the code can't be built because another task's part hasn't landed, the auditor can answer `UNVERIFIED` instead of `FAIL`. The task lands on the patch marked as unverified, and the patch doesn't reach your branch until checks have built and tested it.
- **Ryter offers your project's checks.** With no checks set, once a project has a manifest Ryter works out its test commands and asks you once whether to use them. `Cargo.toml` gives `cargo test`, `package.json` gives its build and test scripts, `go.mod` gives `go build` and `go test`, and Python gets pytest or unittest. You can use them for the session or save them to `.ryter/config.toml`.

## Tried before release

In the TUI, on a new Rust project, with `deepseek-v4.1-flash` as lead and builder, `glm-5.3-prime` as auditor, and three tasks: a scaffold that depends on `pq-sys` (which needs `libpq`, not installed on the test machine), and `greet` and `count`, which build on it.

1. **The scaffold ran alone.** The builder found `libpq` missing and stopped: `STATUS: BLOCKED … To unblock: sudo dnf install libpq-devel`. It made 27 calls, spent $0.02, and had no audit or retry.
2. **`greet` and `count` never started.** The lead asked what to do: install `libpq-devel`, drop the dependency, or leave it.
3. **After I dropped the dependency,** the scaffold was retried and landed. Ryter asked once: "No checks are set … Run these? `cargo test`". I answered yes.
4. **`greet` and `count` then ran in parallel** on top of the scaffold. `cargo test` passed on each (3 and 7 tests), the auditor passed both, and the patch landed as one commit. `cargo test` on the result: 7 passed.

The whole run cost $0.10.
