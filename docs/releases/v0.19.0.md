Two patches since 0.18.0: the small things queued after that release, and five things a real run of the hats showed. On 2026-10-04 Claude drove three small projects, a FastAPI inventory service, a terminal to-do app and a URL shortener, through plan, build, audit and scribe with real models, for $1.22 in all. The flow held each time; this release fixes what a person at the keyboard would have hit.

## Upgrade

```sh
ryter update
```

From 0.8.2 or earlier, run the install script once:

```sh
curl -fsSL https://raw.githubusercontent.com/zypher-systems/ryter/main/install.sh | sh
```

Coming from 0.17.0, these behave differently:

- **The activity strip above the prompt is gone.** The row under the model is the one place a turn's progress shows. `Ctrl+R`, or a click on that row, opens the reasoning right under it, in the conversation; the same closes it. After the turn the pane sits under the turn's receipt line. `[ui] reasoning` keeps its three values with the same meaning.
- **A turn may use 150 rounds** before it stops and asks you to continue, where it used 40. `rounds a turn` in `/settings`, `[limits] rounds` in config, or `--rounds N` for one run change it; `0` lifts the cap and leaves the spend budget as the guard.
- **The scribe, asked for documentation,** writes `README.md` and `docs/guide.md`, not the README alone.
- **On the audit card, Enter closes a pass and repairs a failure.** A card with no failing finding offers `⏎ close · n close`; one with a failure offers `⏎ repair in build · y repair in build · n close`.

## What was wrong

- The run-file card ("how this project runs") floated in the middle of the conversation and covered the build hat's reply, while the allow card had been moved under the chat in 0.17.0. Its note still named the removed test hat.
- The scribe could not look at the product it was documenting: a `curl` GET to the running service's own `/docs` page and the project's own `tasks --help` were both refused, with a message claiming they "change things". The plan hat had the same rule.
- `export F=/tmp/x; rm -f "$F"` and `F=/tmp/x; rm -f "$F"` got different decisions and different card text, because the gate forgot a name that `export` set. Deletion asks either way; the reason shown was wrong for one of them.
- The allow card's title named the first word of a script (`run  set -e`), not the line that asked.
- An audit that posted test data into a running service left it in the product's git-ignored database and still reported that it changed nothing.
- From the 0.18.0 reviews and the queue: the failing audit card offered both `⏎` and `y` for the same action; the round cap's stop message did not name `--rounds`; the allow card's key row lost `n` on a narrow column; an audit with no verdict offered a repair; the classic layout's foot stayed plain while a card was open.

## What changed

- **One key on the audit card.** `⏎` repairs a failed audit in the build hat and closes a passed one; `y` is gone from the legend and the keys. An audit that filed nothing and gave no verdict says `no verdict` in its title and closes on `⏎`, with no repair offered.
- **The round cap's stop message names all three ways to raise it:** *rounds a turn* in `/settings`, `[limits] rounds` in `config.toml`, and `--rounds N` for one run. The guide says the same.
- **The allow card's own key row keeps its keys on a narrow column.** The scope is said in a word, `a allow edits this session`, and a key that does not fit is left out without taking the ones after it, so `⏎`, `a` and `n` are on the row at 100 by 30 and 80 by 24.
- **The classic layout's foot line** shows a card's keys in the warn color while a card is open, as the rack screen's does.
- **The run-file card is a question under the conversation.** "How this project runs" now takes the same inset slot as the allow card, with the reply still in view above it, instead of floating over the chat. Its note reads *ryter runs these without asking*. The foot's `esc` says what the card's `n` key does: `reject` on the run-file card, `not now` on the audit's cost card, `deny` on an allow card.
- **The plan and scribe hats may look at the product.** A `curl` GET or HEAD to the project's own address, saving nothing into the project, and a project program's own `--help`, `-h`, `--version` or `-V` (`.venv/bin/tasks --help`) run in both hats. Anything that sends, saves into the project or does more is refused as before, and the refusal now says the hat *only looks* and what it may run, instead of claiming the command "changes things".
- **`export NAME=value` sets a variable as `NAME=value` does.** The gate used to forget a name that `export` set, so `export F=/tmp/x; rm -f "$F"` asked as an unreadable path while `F=/tmp/x; rm -f "$F"` asked as a scratch-space deletion, with different card text. Both forms, quoted or not, on one line or several, now get the same decision and the same card. `declare`, `typeset`, `local` and `readonly` likewise. What asks has not changed.
- **The allow card names the command that asked.** The title and the `what` row show the segment the gate stopped on (`run  rm -f "$TASKS_FILE"`), not the script's first word (`run  set -e`); the whole script stays in the body.
- **An audit that used the product says so.** When the audit started the product, ran its tests, or called its address, audit.md's Tree section adds that whatever the product wrote to its own data, files git ignores, was not restored, and the card's footer says `product data not restored`. The checkpoint covers tracked and untracked files, as before.

New tests cover the docked run-file card at 160×48 and 100×30 with the chat laid out above it, the looking hats' allowances and refusals segment by segment, `export` against a plain assignment in twelve forms, the asking segment on the observed scripts, and the audit's product-data note in audit.md and on the card.

### Fixed after review

The release PR's external reviews found three defects in the driving-run patch. Each fix has a test that fails on the reviewed code:

- **`declare -n` was stored as a plain value.** The new variable loop kept `NAME=value` from any `declare`, `typeset` or `local`, flags aside, so `G=/etc/passwd; declare -n F=G; echo x > "$F"` resolved `$F` to the project file `G` and ran, while bash follows the nameref and writes `/etc/passwd`. A `-n` nameref is now stored as a pointer and followed where `$F` is read and where `F=…` is written, so `cat "$F"` is judged as the referent's file, a later change of the referent counts, `unset F` forgets the referent and keeps the pointer, `unset -n F` the reverse, and `read F` or `let F=…` make the referent unknown; a referent the gate does not know makes `F` unknown. `-u`/`-l` on a nameref recase the referent's name, as bash does, and a bare `declare -n F` on a value that is not a name leaves the value. `local` outside a function changes nothing, as in bash. Every other flag keeps the value written, with `-u`/`-l` applied, because a dropped name would turn a known deletion into a plain ask that `--always-approve` runs.
- **An audit's use of the product was matched by the ready URL's path, as a substring.** `http://localhost:8000/healthz` matched only a command containing `localhost:8000/healthz`, so `curl localhost:8000/items` did not count, while `localhost:8000` would have matched `localhost:80000`. The match is now the product's host and port as one token of the command, with every loopback spelling (`localhost`, `127.0.0.1`, `[::1]`) as the same machine; another port, a longer port or another host is another address.
- **`run_project test` marked the product used before anything ran.** A missing, unapproved or test-less run file returns an error and runs nothing, yet audit.md said the product's data was not restored. The mark is set as each test command starts.
