A project of several parts is found whole, and you can now see what Ryter keeps for a project and clean it up, with a preview before anything goes.

## Upgrade

```sh
ryter update
```

Coming from 0.43.1:

- **Every part of a mixed project is found.** Ryter used to read the first manifest at the top of the project and stop there. A root `Cargo.toml` hid a `package.json`, and a project with nothing at its top got no commands at all. It now reads every `Cargo.toml`, `package.json`, `go.mod` and `pyproject.toml` at the top and up to three folders down, plus a root `Makefile` when nothing else is there. Fixtures, examples, benchmarks and test folders are left out, and so are workspace members their root runs: read as cargo reads its members, and for Node, a member with tests of its own only when the root's `test` hands the run to it. A nested part's commands run from its folder (`cd web && npm test`), and naming a test or a file narrows the run inside that folder too.
- **The run file says what it reaches.** The approval card shows what the proposed commands cover, and warns first when they leave a part out. A run file you wrote is never rewritten: it is read against the parts found, so a suite that skips one says so when you approve it and at the end of every whole `test` run. What a command reaches is the folder it runs in, after `cd` and options like `npm --prefix web`. A command Ryter can't read, such as `make test`, is said to be unread, never assumed to cover or miss a part. `python3 -m unittest` is proposed only where it collects tests, and pytest where test files sit in a plain folder. The run file's format is unchanged and your approvals stand.
- **`/storage` shows what Ryter keeps, and cleans it up.** It lists the project's sessions with their size and the oldest last use, any recovery copies, and the checkpoints under `refs/ryter/undo/` with the space only they hold in Git. Under the figures are three cleanups: checkpoints no session can reach, sessions unused for 7, 30, 90 or 180 days (`←` `→`) together with the checkpoints only they reach, and recovery copies. `Enter` shows what goes, what you lose with it and what stays, then asks. The yes reads everything again first, and leaves anything that changed since the preview. `ryter storage` prints the same figures and removes nothing.
- **Deleting a session says its checkpoints stay.** It never removed them, and the question now says so and points at `/storage`.
- **A hook script written just before it runs is no longer skipped.** It could fail to start with "Text file busy", and Ryter read that failure as an allow, so a hook meant to deny went unheard. Ryter now tries it again.

## Why

Both features close findings G11 and G17 of the outside review of 2026-10-29 (`docs/gap/2026-10-29.md`). Before, a mixed project's `test` looked whole and covered half the project, and checkpoints grew without bound and outlived their sessions. The hook fix came out of the full check for this release: under load the hook test failed 2 times in 25. `DECISIONS.md` 2026-11-02.

## Good to know

- **A checkpoint is kept** while any session in your Ryter home names its commit, whichever project or folder it was started in, so a linked worktree keeps what it uses. It is also kept while it is less than a day old, since another Ryter may be mid-turn. `review` and `now` stay too. A session whose index can't be read keeps every checkpoint it might name.
- **Only Ryter's own refs go.** Only direct refs under `refs/ryter/undo/` are removed, never through a symbolic one, and branches, tags, stashes and commits are untouched. Ryter does not run `git gc`, so Git gives the space back when it next collects garbage. The preview says roughly how much, on Git 2.38 or later.
- **Spend totals.** The project's spend total keeps what a removed session cost. A rebuild of that total, which happens only when a session's log is found rewritten, counts only the sessions that are left.
- **Commands across parts.** In a project of several parts, `build`, `check`, `lint` and `format` share one line per verb, so the first failure stops the rest. The fast check after an edit runs every part's check.
- **Makefile beside nested parts.** A root `Makefile` is proposed beside the nested parts. If its `make test` already runs one of them, that part can run twice; take the duplicate off on the card.

## Tried before release

The full local check (1,144 tests) and CI on Linux and macOS. The review's layouts as tests, the Cargo and Python ones checked against `cargo metadata` and `python3 -m unittest` themselves. After the review's fixes, discovery on the same checkouts changed only where it had been wrong: one Python project whose tests `unittest` could not collect now gets pytest. Discovery ran read-only on 35 real checkouts, in under 35 ms each, and `ryter storage` read-only on three real repositories, in about 20 ms each. The real TUI on the simulated provider: an approved run file across two parts, and a narrowed run in a nested folder. Also in the TUI, at 80×24 and 120×40: `/storage` removing nine checkpoints no session reached while keeping the two made that day, and a 45-day-old session removed while the open one stayed.
