Two Ryters with the same session open no longer lose each other's messages, a session's files are readable by your account alone, and two gaps in the command gate that the 0.43.0 reviews left are closed.

## Upgrade

```sh
ryter update
```

Coming from 0.43.0:

- **A compaction keeps what another Ryter appended.** With the same session open in two Ryters, a compaction in one rewrote the transcript from its own memory, so what the other had said since was gone. Each instance now checks the transcript file, by its length and a hash of its bytes, before writing to it: rows another Ryter appended are taken in, a transcript rewritten elsewhere is followed, and a compaction made from a transcript that is no longer the file's is refused, with the turn saying so. Two Ryters interleaving one conversation is still not something that works; neither loses the other's words any more.
- **Session files are private.** A session's folder and its logs were created with the process's default mode, 0755 and 0644 under the usual umask, so another account on the machine could read a transcript wherever the folders above let it in. They are now 0700 and 0600 by mode, whatever the umask, and an older session's folder and logs are tightened when it is opened.
- **A `git` option the gate can't read is refused.** `git -c $(x) status`, `git -c $v status` and `git -c$(x) status` ran where the written setting is refused: a setting can name a program to run. They are refused as a verb the gate can't read is, and the model is told to write the setting out. `--config-env=alias.x=NAME` is refused too: the alias body is the variable's, which the gate is not looking at.
- **`set` with positionals is found behind a wrapper.** `builtin set -- …`, `command set -- …`, `time set -- …` and `FOO=1 set -- …` planted `$1` and `$@` past the refusal 0.43.0 added for `set -- …`. They are the same `set`, and refused.

## Why

A review of dev the day after 0.43.0 reproduced all four through the storage API and the gate. The two gate gaps were named in the 0.43.0 reviews and carried over; the two session faults are older than any release. `DECISIONS.md` 2026-11-01.

## Good to know

- The session store detects a second Ryter rather than locking it out: opening a session twice is how `/sessions`, `ryter sessions` and a resume read one.
- None of these forms appears in the 1,573 commands and sessions replayed from real use. The replay's verdicts are the same as 0.43.0's.
- The store reads the whole transcript file at each append to check it; a transcript is small next to a model call.
- Open from 0.43.0, unchanged: a reader handed a whole substitution (`cat $(…)`) passes under the standing ruling for a path the gate can't see; the card and the tool row drop a tab in a command's display.

## Tried before release

The full local check and CI on both patches; three new tests that fail on the 0.43.0 store and pass on this one; the replay of 1,573 real commands and the 229 commands the 0.43.0 reviews named, with no verdict changed from 0.43.0; the real TUI on the simulated provider, whose fresh session came out 0700/0600 through a turn.
