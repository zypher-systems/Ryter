The build hat can ask to run a command as root. When the work needs a system package, the model runs `sudo <command>`, you say yes on a card that shows the whole command, and sudo's question for your password comes up in a panel in Ryter. What you type goes to sudo and nowhere else.

## Upgrade

```sh
ryter update
```

From 0.8.2 or earlier, run the install script once:

```sh
curl -fsSL https://raw.githubusercontent.com/zypher-systems/ryter/main/install.sh | sh
```

Coming from 0.22.0, these behave differently:

- **`sudo` is no longer refused outright in the build hat.** `sudo <command>`, written plainly, asks; every other spelling, every other hat, and `su`, `doas` and `pkexec` are refused as before. `/yolo` and `/tools always` do not answer the question.
- **A `SUDO_ASKPASS` of your own is not passed to the commands Ryter runs.** An approved root command gets Ryter's; a script that calls `sudo -A` itself, outside one, no longer reaches your desktop's askpass.
- **The first approved root command adds two files to `~/.ryter/bin`:** a `sudo` wrapper and a `ryter-askpass` link. Nothing is installed outside `~/.ryter`.

## What changed

- **The build hat can ask to run a command as root.** When the work needs a system package or another command as root, the model runs `sudo <command>` and you are asked, twice over. First a card, "run as root", showing the whole command: only `y` runs it, there is no "always", and `/tools always`, `--always-approve`, your `[permissions]` rules and `/yolo` do not answer it. Then sudo's own question for your password, in a panel in Ryter. What you type is shown as dots and goes to sudo only: not to the model, not into the conversation, not to the session's log or to disk.
- **The password can be kept for five minutes.** That is the default, in memory only, so a second root command shows its card and runs. `Tab` on the panel turns it off. A password sudo turns down is dropped and asked for again, and the panel says so.
- **Root opens nothing that was refused.** The command after `sudo` is judged as the build hat's own first: `sudo bash -c …`, `sudo systemctl …`, `sudo chown …`, a secret file and a write to `/etc` by name are refused as before. Only the plain spelling is read, in a call of its own (nothing before it on the line but a `cd` or another `sudo <command>`); sudo's own options, a wrapper in front of it, and `su`, `doas` and `pkexec` stay refused, and the refusal tells the model the spelling that works.
- **Root is not handed what your account can't read.** A root command that names a file you may not open, or a folder that holds one at any depth, is refused (`/etc/shadow`, root's folder, a disk in `/dev`, `sudo grep -r . .` over a file you can't read), and so is one whose files can't be seen before it runs (`sudo cat $F`, `sudo xargs cat`, `sudo find … -exec`). Programs that only list or remove are not held to the folder rule, so `sudo rm -rf` of a folder a container left behind asks.
- **No program that runs a text of its own, as root.** `sudo python3 x.py`, `sudo sh install.sh`, `sudo awk`, `sudo sed`, an editor or a debugger are refused, under their versioned names too. A program of the project's own runs (`sudo ./install.sh`, `sudo make install`): the card shows you the command, and the yes is yours.
- **Where it is not offered.** Plan, scribe and audit; headless runs; `.ryter/run.toml`; and any sandbox profile but `off`, under which the system stops `sudo` from gaining privilege. In each the model is told to name the command for you.
- **Only Ryter's askpass answers for a command Ryter runs.** `SUDO_ASKPASS` is taken out of every command's environment except an approved root command, where it names Ryter's.

Guide: "As root".

## Why

On a real run a Rust project needed the ALSA development headers. `sudo dnf install` was refused, as every `sudo` was, and the model did what models do with a wall: it spent fifteen calls on workarounds, then restructured the project so the part that needed the package was never built. The plan was no longer the plan, and nothing on screen had asked. The user's words: "if it wants to run a command with sudo and I am ok with it I should be given a prompt to type in sudo credentials."

## Good to know

- Nothing is installed outside `~/.ryter`: a `sudo` wrapper and a `ryter-askpass` link in `~/.ryter/bin`, used only for a root command you approved. Ryter itself never runs as root.
- What a root command changes, `/undo` does not put back.
- A wrong password counts against your account as it would in a terminal; where `pam_faillock` is on, a cancelled panel can count too.
- Linux and macOS.

## Tried before release

- **Driven in the real binary,** offline against the simulated provider, with a stand-in `sudo` that calls the askpass as `sudo -A` does and never authenticates: the card, Enter ignored on it, `y`, a password turned down and the panel saying so, a second accepted, the next root command answered from memory, `sudo -n` refused with its hint, a card denied, `Esc` on the panel, and `Ctrl+C` with the panel open. The typed password was in no request to the model, no event of the session's log and no file under the Ryter home.
- **Seventy spellings through the gate** before the merge, among them globs, a `cd` and a relative name, links into `/etc`, and recursive reads. Six let root print what the account could not read (`find -exec`, `xargs`, an unknown `$VAR`, `~root`, a raw disk, an interpreter); each is refused now and has a test.
- **The whole test suite** on Linux and, in CI, on macOS: 745 tests pass, with the acceptance suite, both benchmark steps, the install script's test and the licence bundle, each gated on its exit code.
- **Not yet tried:**
  - A real `sudo` authentication, with a real password, on Linux or macOS. The stand-in proves the path to the askpass and back, not sudo's own handling of it.
  - Anything on a Mac by hand.

### Fixed after review

The release PR's external reviews approved once and rejected once, on four ways an approved root command could still print what your account cannot read:

- **A folder you can list was treated as open.** `sudo grep -r . /etc/security`, `sudo tar cf - /home` and `sudo grep -r . .` over a file you can't read all asked. A root command handed a folder is now refused when anything in it, at any depth and through links, is closed to your account.
- **The interpreter refusal went by exact name.** `python3.12`, `busybox ash`, the system loader handed an interpreter, `awk` and `sed` got past it. Names are matched without their version, the list is longer, and a path to an interpreter among a command's arguments is refused.
- **An earlier command on the line could make what the root command named** (`python3 -c '…symlink…' && sudo cat link`). A root command now runs in a call of its own.
- **A pipe or a socket nobody may read counted as readable.** The system is now asked, whatever the kind of file.

A paste of several lines into the password panel now takes the first line only.
