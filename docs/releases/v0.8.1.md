Ryter no longer turns a folder of projects into one git repository. Started in a folder like `~/workspace` that holds other projects' repositories, crew mode stops before it does anything and tells you to start in the project's own folder. Solo mode still edits, but doesn't set up git there. When the project cost is counted for a folder above the one you started in, the rail now says which folder.

## Upgrade

```sh
curl -fsSL https://raw.githubusercontent.com/zypher-systems/ryter/main/install.sh | sh
```

## What was wrong

- **Ryter made `~/workspace` a repository.** A crew session started there on 2026-09-28 ran `git init`. It committed the 68 files at the top as the starting point, sweeping 29 project repositories into one new repository. It also wrote `ROADMAP.md`, `DECISIONS.md` and `notes/` there. Ryter only refused to do this in the home folder and at `/`.
- **So the project cost looked stuck.** Every project inside `~/workspace` counted toward that one repository. The total was the same whichever project you started in, and nothing on screen said why.
- **A failed turn closed with "✓ answered"** under its error.
- **Two small things from the 0.8.0 review:**
  - A headless run told the model that the user's settings kept a page closed.
  - `load_skill` read a hidden file in a skill's folder if the model named it, though the skill's file list leaves hidden files out.

## What changed

- **A folder of projects is left as it is.** That's a folder that isn't a repository with commits, but holds repositories in its folders or one level further down (`clients/acme`).
  - **Crew mode** stops at your first message, before any model call, with nothing written. It names the repositories it found. For a folder of projects, it says to start Ryter in the one you mean: `cd alpha && ryter`, or `mkdir myapp && cd myapp && ryter` for a new one. If the repositories are the project's own dependencies, it says to add their folder to `.gitignore`.
  - **Solo mode** still edits files, but doesn't set up git for `/undo` there, and says so.
  - **What doesn't count:** repositories in folders git will ignore, since they stay out of the first commit anyway. That means your folder's own `.gitignore` rules, or, when there's no `.gitignore`, the one Ryter writes (`node_modules`, `target`, `.venv`, caches). They apply in git's order: a `.gitignore` in a subfolder outranks the one at the top.
  - **Git has the last word.** Before the first commit, Ryter asks git what the commit would hold, without touching your staging area. If that includes another repository at any depth, Ryter refuses and undoes what it did: the `.git` it made and the `.gitignore` it wrote.
  - **If you do want one repository there,** run `git init` and make the first commit yourself. Ryter then works in it as usual.
- **The rail names where the project cost is counted** when that's a repository around the folder you started in. The line appears under `project`, for example `in ~/workspace`. The project column in the `$` drawer is named for that folder too.
- **A failed turn closes as `✕ failed`.**
- **Pages:** a headless run is told it's headless.
- **Skill files:** `load_skill` refuses a hidden file in a skill's folder.

This covers the part of the "What 1.0 means" item "Ryter only touches the project it was started in" about creating repositories.

### Fixed after review

Three external reviews of the release PR each found a way for a repository to reach the first commit. All three are fixed.

**First review.** It found a hole in how dependency folders were left out. They were skipped by name (`node_modules`, `target`, …) even when the folder already had its own `.gitignore` that didn't ignore them. The reviewer's two cases both used a `.gitignore` holding only `*.log`:
- **A new folder with a repository in `node_modules/pkg`:** Ryter set up git anyway, and the first commit held that repository.
- **An unborn repository with a repository in `target/pkg`:** the same happened.

Now the folder's own ignore rules decide what counts (its `.gitignore` files and `.git/info/exclude`), and Ryter's first `.gitignore` counts only where it will be written. Both cases are tests, and both fail on the first version. A third test checks that folders ignored at either level, or by `.git/info/exclude`, still don't count, and that the commit holds no other repository.

Then in the TUI, with a git repository in `node_modules/pkg`:
- **A folder whose `.gitignore` held only `*.log`:** the crew stopped at once and named `node_modules/pkg`. The first message then told you to `cd node_modules/pkg`, which is wrong for a dependency. Both messages now also say to add the folder to `.gitignore` if the repositories are the project's dependencies.
- **After adding `node_modules/` to that `.gitignore`:** a solo edit set up git, and the first commit held only `.gitignore` and `index.js`.
- **A folder with no `.gitignore`:** a solo edit set up git with Ryter's `.gitignore`, and again `node_modules/pkg` stayed out of the commit.

**Second review.** Where there was no `.gitignore`, Ryter's template was applied as an overriding rule. In git, though, a `.gitignore` in a subfolder outranks the one at the top. With `web/.gitignore` holding `!target/`, git put `web/target`, a repository, in the first commit, and Ryter didn't see it. Two fixes:
- **The check follows git's order:** the nearest `.gitignore` first, then the top one (or the template), then `.git/info/exclude`.
- **Git itself checks the first commit** before it's made, at any depth, as described above.

The reviewer's case is a test, and so is a repository three levels down, deeper than the first check looks. Both fail on the reviewed code. In the TUI:
- **The reviewer's case:** crew mode stopped at once and named `web/target`.
- **A repository at `a/b/c`:** a solo edit went ahead without setting up git. The message named `a/b/c`, and the folder was left with no `.git` and no `.gitignore`.

**Third review.** Git's check started from an empty index. In a repository with no commits yet, you may already have staged something yourself, and ignore rules don't take a staged repository out again. The reviewer staged `target/pkg` by hand and then ignored `target/`. The check didn't see it, and the first commit held it. Now:
- **The check starts from a copy of your index,** so it stages exactly what the commit would hold. Your real index stays as it was.
- **The crew's early check also reads what's already staged** in such a repository, so the crew stops before any model call.
- **A check that can't run refuses too.** For example, git can't stage a repository with no commit of its own. Ryter used to return the error but leave the `.git` and `.gitignore` it had just made. Now it undoes them, as with any other refusal.

The reviewer's case and the check that can't run are tests, and both fail on the reviewed code. In the TUI, with `target/pkg` staged by hand in a repository with no commits:
- **Crew mode** stopped at once. It said the repository has no commit yet and named `target/pkg`.
- **Your staging area** still held `target/pkg`, and there was still no commit.
