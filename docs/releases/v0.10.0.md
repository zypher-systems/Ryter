Ryter now keeps your own rules for every project, and the model can save one when you tell it to, once you've approved the change. The benchmark has grown into a suite of real multi-file tasks in three languages, and its results are published and compared from one release to the next.

## Upgrade

```sh
ryter update
```

From 0.8.2 or earlier, run the install script once:

```sh
curl -fsSL https://raw.githubusercontent.com/zypher-systems/ryter/main/install.sh | sh
```

## What was wrong

- **Ryter had rules for a project, but none for you.** A project's `RYTER.md` reached the model, but there was nowhere to put rules that hold in every project. The nearest thing, `~/.ryter/prompts/`, replaces Ryter's own instructions and doesn't add to them. The model also had no way to save a rule when you told it one.
- **The benchmark was too small to say much, and its results lived nowhere.** It had four Python tasks of one or two files each. A run printed its numbers and that was all: nothing was published, and nothing said whether a release did better or worse than the last. It also named the wrong builder: it printed the config file's default model when the builder was following the lead.
- **A shell-tool test failed now and then in CI.** It starts a background process that detaches itself with `setsid`, then checks that Ryter stops waiting for it. On a busy machine, the command could finish, and Ryter could stop its process group, before `setsid` had detached. Ryter then correctly reported that it had stopped the background process, but the test expected the other outcome. Ryter behaved correctly both ways.
- **Two of these tests used `pkill -f` and `pgrep -f`** to find their process by a pattern, and needed `setsid`, `pkill` and `pgrep` to be installed.

## What changed

- **Your rules, for every project: `~/.ryter/RYTER.md`.** Ryter puts the file into the instructions of every role on every message, ahead of the project's own `RYTER.md`. Where the two differ, the project's win. Edit it by hand whenever you like.
- **The model can save a rule when you tell it one.** Say "from now on…", or type `/rules <what to remember>`. A new built-in `rules` skill covers when a rule is worth saving, which file it belongs in, and how to write it. A new `update_rules` tool makes the change.
- **Nothing is saved without you.** Ryter shows the change line by line and asks every time.
  - The prompt holds the whole change: every changed line, with long lines wrapped. A long change scrolls with `↓` and `PgDn`.
  - Only `y` saves it, and only once every row of the change has been drawn on screen. Ryter counts the rows it has drawn, so pressing `PgDn` many times at once skips nothing. There's no "always", and `--always-approve` doesn't skip it.
  - In a window too small to show any of the change, the prompt says so and `y` does nothing.
  - A change holding a character the screen wouldn't show as it is, such as a control code or an invisible character, is refused before you are asked.
  - If you say no, the file is left as it was.
  - A headless run saves nothing.
  - Under `--sandbox` the file can be read but not changed.
  - If you edit the file yourself while the question is on screen, your edit is kept and nothing is saved over it.
- **The benchmark is a suite of real tasks.** It has nine tasks now, up from four:
  - **A feature across four Python modules,** one of them new.
  - **Bugs in two Python modules** that only show together.
  - **A Rust crate:** a parser, its errors and a formatter, across three modules.
  - **A TypeScript library,** run by Node with no build step.
  - **One piece of work split into three builder tasks,** as an architect's plan splits it: two run side by side, and the third waits on both.

  A task says which tools it needs, and is skipped, by name, on a machine without them.
- **`ryter bench --publish docs/bench`** writes the run as a page (`docs/bench.md`) and as data (`docs/bench.json`). It also says how the run compares with the one published before, and names any task that ran last time and not this time. Cost is shown but never counted as worse, because the same crew can take several times as many steps on one run as on the next.
- **The published run is replaced only by a run that can stand in for it.** Otherwise it is left exactly as it was, and `ryter bench` exits 1:
  - when a task is accepted less often, or passed wrong more often, counted per run of the task;
  - when a task of the published run was skipped on this machine;
  - when only part of the suite ran (`--publish` refuses `--only`).
- **A run that measured nothing fails.** With or without `--publish`, `ryter bench` exits 1 when every task was skipped. It stops at the first task no model answered, says why, and spends nothing on the rest. That covers a refused key, a model the account can't reach, and a crew that won't start. `--repeat 0` and `--budget-usd 0` are refused.
- **The benchmark names the models that ran.** A seat with no model of its own is shown with the lead's.
- **The shell tool's background tests can't race.** Nothing changes in how Ryter works.
  - The background job now writes its process ID to a file before the command goes on. The test that detaches it gives it its own process group through job control (`set -m`). It has left the group before Ryter could stop it, so the race can't happen.
  - Both tests find their process by the ID it wrote. They clean up by that ID too, with no pattern matching and no extra programs.

## Tried before release

- **Your rules, in the TUI with deepseek-v4.1-flash:**
  - **Saving:** I told it "From now on, always answer me in British spelling. Save that as one of my rules for every project." It loaded the `rules` skill and called `update_rules`. The prompt showed the three new lines of `~/.ryter/RYTER.md`, with only *y allow once* and *n deny*. After `y`, the chat said "rules · saved to ~/.ryter/RYTER.md", and the file held the rule.
  - **A brand-new session:** asked to quote my standing rules, it quoted that rule exactly, and wrote "centre" in its next sentence.
  - **Saying no:** `/rules remove the British spelling rule` showed the removal as a diff. I answered `n`. The file was unchanged, and the model said so.
- **A long rules change, in the TUI against a stand-in provider** that asked to replace a one-line file with 49 lines, one of them over 600 characters long:
  - **At the top:** the prompt showed the first 15 rows and "↓ 40 more rows · read to the end (↓ PgDn), then y". `y` saved nothing and said there was more to read.
  - **Paging down:** every row passed through the prompt, and the long line was wrapped over seven rows to its last word.
  - **At the end:** `y` saved the file, and it held exactly the 49 lines. The chat said "rules · saved to … (+49 −1)".
  - **In a 16-row terminal:** the prompt showed two rows of the change at a time and still reached the end. `n` there left the file as it was.
  - **Resized part-way through:** the change was laid out again at the new width, and `y` still waited for the end.
  - **Hidden text:** a change carrying an instruction in invisible characters never reached the prompt. The model was told why, and the file was unchanged.
- **Keys sent faster than the screen draws,** in the TUI with a 103-line change:
  - **Thirty `PgDn` presses at once, then `y`:** the prompt moved on by one screenful per frame, and `y` saved nothing.
  - **To the end in bursts** of three `PgDn` and a `y`: every rule from 1 to 100 was on screen before a `y` saved the file, and it then held all 103 lines.
  - **A 9-row terminal:** one row of the change fits. Pressing `y` early didn't push that row off, and twelve rules were read one at a time before `y` saved them.
  - **An 8-row terminal:** one row of the change fits. Sixty `PgDn` presses at once moved it on by that one row, and `y` saved nothing.
- **The benchmark, run three times with a real crew** (lead and builder deepseek-v4.1-flash, auditor deepseek-v4-pro, $1 cap per task):
  - **The first two runs:** 9 of 9 landed, 9 of 9 passed the hidden tests, and no wrong work got past the auditor. The second is the published run.
  - **The third run:** 9 of 9 landed and 8 of 9 passed the hidden tests. On the TypeScript task the builder's `once` left `off` unable to remove the handler, and the auditor passed it: one false pass.
  - **Cost:** $0.199, $0.204 and $0.317 in total. One task cost $0.03 on one run and $0.16 on another.
  - **The split task:** its two independent parts started together, and the third ran once both had merged.
  - **The comparison:** the second run was published over the first, printed "accepted 9/9 then, 9/9 now" and exited 0. The third was published over a copy of the second. It printed "ts-event-bus: WORSE, accepted 1/1 then, 0/1 now", exited 1, and left the copy as it was.
  - **What this does and doesn't show:** the whole pipeline works across three languages and a split plan, and a release that breaks it would show up here. Over three runs the crew was right 26 times in 27, and the hidden tests caught the one time the auditor was wrong. One run of nine tasks is a small sample: the same crew scored 9 of 9 twice and 8 of 9 once. The suite still can't tell a good crew from a better one. Harder tasks, and more runs of each, are next on the roadmap.
- **The benchmark as a gate,** with the real program against a stand-in provider that refuses every key. Each of these exited 0 before, and the first replaced the published results with none:
  - `--repeat 0 --publish`: refused, exit 1.
  - Every seat on one model: stopped at the first task with "no model answered … builds paused", exit 1.
  - A refused key: stopped at the first task with "the key was refused", exit 1. Published where nothing was published yet, it wrote no files.
  - A suite whose tools are all missing: "every task was skipped", exit 1.

  In every case the published page and data were byte for byte what they had been.
- **The suite itself:** a test checks every task. The hidden tests fail on the starting code and pass on a reference solution. All nine were checked on a machine with Python, Rust and Node.
- **The shell tests:** the fixed tests passed 15 runs out of 15 with every CPU core busy.
