Ryter learns to look things up. The plan and audit hats can ask what version of a dependency is current and what is known against it, from the package registries and OSV.dev, with no key and no setup. And web search goes through a provider you choose, Tavily with a key or a SearXNG server of your own, in place of a scrape of a search page that nobody had turned on.

## Upgrade

```sh
ryter update
```

From 0.8.2 or earlier, run the install script once:

```sh
curl -fsSL https://raw.githubusercontent.com/zypher-systems/ryter/main/install.sh | sh
```

Coming from 0.20.0, these behave differently:

- **`[features] web` is on by default.** A `web = false` you set yourself in `settings.toml` still holds. With it on, `web_fetch` refuses every private address as before, and `web_search` searches nowhere until you choose a provider.
- **`web_search` needs a `[search]` section.** `provider = "tavily"` with a key (`ryter connections set-key tavily`, or `/provider set-key tavily`, or `TAVILY_API_KEY`), or `provider = "searxng"` with the `url` of your server. Without one the tool refuses and says what to set. The DuckDuckGo scrape is gone.
- **The web is the plan and audit hats'.** `web_search` and `web_fetch` are refused to the build and scribe hats, with a note naming who uses them.
- **A new tool, `check_package`,** in the plan and audit hats.

## What changed

- **The plan and audit hats can ask after a dependency.** `check_package` gives a dependency's latest release and its known security advisories in one call: the version and its release date from the package's registry (crates.io, npm, PyPI, the Go module proxy), and the advisories on record for the version in use from OSV.dev, each with its aliases, its severity where the record gives one, a one-line summary and the versions that fix it. Fixed public hosts, read-only, no key, on by default, and no `[features] web` needed. The plan hat is told to ask before it pins a version; the audit hat to ask what is known against the dependencies. The build and scribe hats are refused it and told who asks.
- **`web_search` looks where you tell it to.** `[search] provider = "tavily"`, with a key stored like a connection's, or `provider = "searxng"` with the `url` of a server of your own. Each result comes back as its title, address, date where known and a snippet; `max_results` is yours (1 to 10, 5 by default). `[features] web` is on by default, and `web_search` and `web_fetch` belong to the plan and audit hats, as `check_package` does; a refusal with the feature off says where it is turned on. The guide has a "Web search" section with both configurations.
- **`ryter connections set-key` takes a search provider's name** (`set-key tavily`) as well as a connection's.

## Why

Building anything means knowing what is current and what is broken. The registries and OSV.dev answer that question exactly, for nothing, so that is the first thing Ryter learns to look up. Where the tools sit is the user's placing: research is the plan hat's, findings are the audit's, the build hat carries out a plan and the scribe documents what is there. The search provider is the user's choice too: Tavily for its free tier, and SearXNG beside it so that nobody is made to take a key.

## Tried before release

- **With a real model, under a $1.00 cap:** `claude-opus-5.5` in the plan hat on a scratch project with three pinned npm packages. `check_package` was called once per package, unprompted as to how, and read back correctly: eleven advisories against fastify 4.0.0 with their fixing versions, none against @fastify/cookie 9.0.0, four against lodash 4.17.15. `web_search` through Tavily returned eight results with snippets on the second turn; the first turn found the `[search]` section was being dropped by the config file reader, fixed before this release with a test that loads a file with the section and reads it back. Told search was off, the model fetched the Fastify v5 migration guide with `web_fetch` on its own and summarised it accurately. The two turns cost $0.17.
- **The whole test suite** on Linux: 726 tests pass, with the acceptance suite, both benchmark steps, the install script's test and the licence bundle, each gated on its exit code. New tests cover the registry documents and OSV records on fixtures, the two search providers' answers read as one list, the config section, the gate for each tool in each hat, and the refusals' wording.
- **Not yet tried:**
  - SearXNG live.
  - The audit hat using either tool with a real model.
  - Anything on a Mac by hand.
