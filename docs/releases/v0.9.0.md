Ryter now keeps itself up to date. When it starts, it checks for a newer release, installs it in the background, and tells you to restart to use it. `ryter update` does the same whenever you ask. Every update is signed, and Ryter refuses any that isn't signed with its release key.

## Upgrade

This is the last time you need the install script:

```sh
curl -fsSL https://raw.githubusercontent.com/zypher-systems/ryter/main/install.sh | sh
```

## What was missing

- **Updating meant rerunning the install script,** and nothing told you a new release was out.

## What changed

- **At launch, at most once a day,** Ryter checks GitHub for the latest published release. If it's newer, Ryter installs it in the background and says in the chat: "Ryter 0.9.1 is installed. Restart Ryter to use it." The Ryter you're running keeps working until you quit it. The check doesn't hold up startup, and if you're offline it says nothing and tries again next time.
- **`ryter update`** checks and installs now. `ryter update --check` only says whether a newer release is out.
- **You choose what happens at launch** in `/settings` → *updates* → *on launch*, or `[update] mode` in `config.toml`:
  - `install`, the default;
  - `notify`, which tells you and leaves installing to `ryter update`;
  - `off`.

  Headless runs (`ryter -p`) never check.
- **Before Ryter installs anything,** it checks three things:
  1. **The signature.** The release's checksums must be signed with Ryter's release key. Ryter is built with the public half of that key, so a tampered release, or one signed with any other key, is refused.
  2. **The checksum.** The download must match.
  3. **The binary itself.** It must run and report the version the release says.

  Only then does it swap in the new binary, the same way the install script does.
- **When Ryter won't replace itself,** it says why and what to do:
  - **A build from source** (`cargo build` or `cargo install`) updates the way you built it.
  - **A binary in a folder you can't write to,** such as one installed under `/usr/local/bin` by another account, is left alone, and Ryter never asks for `sudo`.
- **Releases are now signed by the release workflow,** and it refuses to draft a release whose signature doesn't match the public key in the repository.

## Tried before release

Everything was tested with a throwaway signing key and a signed 0.9.1 served from this machine. The real key signs the first time with 0.9.0's own release.

- **In the TUI:** Ryter 0.9.0, installed in a folder of its own, started up and said "Ryter 0.9.1 is installed. Restart Ryter to use it." The installed binary then reported 0.9.1, with nothing left behind. `/settings` shows *updates · on launch ‹ install ›*.
- **`ryter update --check`** reported 0.9.1 and installed nothing. **`ryter update`** installed it.
- **Refused, with the installed binary untouched each time:**
  - a release with no signature;
  - a download changed by one byte;
  - a folder Ryter couldn't write to. Its message gives the install script with `RYTER_INSTALL_DIR` set to that folder.
  - a plain cargo build.
- **With the real release key in place**, a release build checked GitHub and reported that 0.9.0 is the latest. Every release so far has the checksums and downloads Ryter fetches, but no signature, so Ryter would refuse to install any of them.
- **A bug found while testing, now fixed:** the first version told a development build by its path (`…/target/release/`) and missed one in a `target-updtest/` folder, which it replaced. Now only binaries the release workflow built replace themselves.
- **Tests:**
  - a signed release installs;
  - a forged or missing signature, a wrong checksum and a wrong-version binary are each refused;
  - drafts and pre-releases aren't offered;
  - development and cargo builds are refused;
  - the launch check installs or notifies, at most once a day.

  A separate test signs with `openssl`, exactly as the workflow does, and Ryter verifies it.

### Fixed after review

The release PR's first external review found that a release could hang `ryter update`. The new binary's version check had no time limit, so a correctly signed binary that hangs when asked its version would hang the update for ever, with its temporary file left behind. The reviewer reproduced it with a signed binary that runs `sleep 30`. Now:
- **The new binary has 10 seconds to report its version.** After that, it and anything it started are stopped, nothing is installed, and the update file is removed.
- **Its output is read only up to 4 KB.** A binary that floods its output can't fill memory. One that leaves a background process holding its output open can't hold the update up either.
- **It gets no input,** so it can't read your keystrokes in the TUI.
- **Leftover update files** from an update that was interrupted, by quitting Ryter mid-download for instance, are cleared on the next update.

The second review approved the PR, and its follow-up is fixed too. A cargo build copied out of its `target/` folder still checked at launch, then said it couldn't install. Now any cargo build is told plainly that a newer release is out and how to update it the way it was built. `ryter update --check` says the same, and never that `ryter update` installs it.

The new tests cover a signed binary that hangs, one that floods its output, and one whose child holds its output open. The hang test takes 30 seconds against the reviewed code and passes in about 1.5 seconds now. In a live run against a signed release served locally, `ryter update` stopped after 10 seconds with "the new binary didn't report its version within 10 s; nothing was installed". The installed binary was unchanged, and no process from the probe was left running.
