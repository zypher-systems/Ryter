The model can now pick up skills by itself, and it can show you a page in your browser: a report, a comparison or a chart that a terminal shows badly. Ryter's first built-in skill, `canvas`, teaches it how to make one.

## Upgrade

```sh
curl -fsSL https://raw.githubusercontent.com/zypher-systems/ryter/main/install.sh | sh
```

## What was missing

- **Skills only worked when you typed them.** A skill's instructions reached the model only through its slash command. The model never knew which skills existed, so it couldn't use one when a task called for it.
- **Everything had to fit in the terminal.** A comparison across a dozen files, a chart, or a plan to scan came back as a wall of text or a table cut at the terminal's width.

## What changed

- **The model sees the skills and loads them itself.** Its instructions list every skill it may use, by name and one-line description. It reads one with `load_skill` when a task calls for it. You can still start any skill with its slash command. `model-invocable: false` in a skill's frontmatter keeps it to the palette. A skill in `~/.ryter/skills`, or a trusted project's `.ryter/skills`, replaces a built-in one of the same name.
- **A skill can carry files**, such as a template or a checklist, in its folder next to `SKILL.md`. The model sees their names when it loads the skill and reads one with `load_skill` and `file`. It can read only files inside that folder.
- **Pages.** When an answer suits a page better, the model loads the `canvas` skill, writes one self-contained HTML page and shows it with the new `show_page` tool. You can also ask for one with `/canvas <what you want to see>`. The skill covers:
  - using only facts from the session, with a line saying where they came from;
  - a clear structure;
  - light and dark themes, and phone width;
  - readable contrast;
  - charts drawn in SVG.
- **Where pages go:** `~/.ryter/pages/<session>/<title>.html`, never into your project. Showing a page with the same title replaces it, and deleting a session deletes its pages.
- **Ryter opens the page in your browser** when there's a desktop, and the chat always links it. `/settings` → *pages in browser* (`[ui] open_pages = false`) keeps pages closed, with the link only. Under `--sandbox`, pages stay closed too.
- **A page loads nothing from the network:** no scripts, fonts or images from the web, and no form posts. Ryter puts a Content-Security-Policy at the very top of every page, ahead of anything the page contains.
- **Your hooks see the new tools.** `PreToolUse` and `PostToolUse` run for `show_page` and `load_skill` (and `request_hat`), so a hook can deny a page.
- **Both work under `--sandbox`:** pages can be saved, and your own skills in `~/.ryter/skills` can be read.

This covers part of "the model has the tools the job needs", one item of the roadmap's "What 1.0 means" list. Seeing images and a browser to look at your app come later.

## Tried before release

In the TUI, in a small Python project (three modules and two test files), in the build hat, with deepseek-v4.1-flash:
- **"Make me a page that shows each Python module: its functions, which tests cover each, and which have no test."** With deepseek-v4.1-flash the model loaded `canvas` and showed a page. Rendered headless, it was correct and clean in both light and dark: 6 functions, `text.slugify` untested, and `stats.median` tested on odd-length input only, with the sources named.
  - The first run also wrote the page into the project with `write` and left a helper script there.
  - The skill and the tool now say to pass the page straight to `show_page` and create nothing in the project.
- **"Show me a page comparing the modules,"** in a new session: the model loaded the skill, read the files, and showed a page with a table and an SVG bar chart. The project was untouched.
  - The link fit on one line in the chat. In the first version, pages lived in the session's folder and the link wrapped over three lines.
- **A bug found in testing, now fixed:** the first runs opened the page in the browser even with `open_pages = false`, because the settings file ignored the key. The last run left the page closed. The tool's reply now also tells the model plainly whether the page was opened, so it can't say it was when it wasn't.

### Fixed after review

The two external reviews of the release PR found four problems. All four are fixed:
- **The network lock could be sidestepped.** Ryter put it at the first `<head>` in the text. A `<head>` inside a comment, or a script placed before the real head, let the page load from the web first. In headless Chromium both pages reached a local server. The lock now comes before the whole page. A test in a real browser shows the sealed pages load nothing, and the same page unsealed does load.
- **Hooks skipped the new tools.** `show_page`, `load_skill` and `request_hat` ran without your `PreToolUse` and `PostToolUse` hooks. Now they go through them, and a test shows a deny hook stops a page.
- **The sandbox broke both tools.** It didn't allow writing `~/.ryter/pages` or reading `~/.ryter/skills`. A browser opened from it would also have run inside the sandbox. Now pages can be saved and skills read, and Ryter doesn't try to open a browser from a sandboxed thread. It now counts a page as opened only when the opener didn't fail.
- **A skill's own files couldn't be read.** The model was given the skill's folder, but `read` treats `~/.ryter` as secret. Now `load_skill` reads them itself.

Then in the TUI, under `--sandbox workspace`, with deepseek-v4.1-flash and a test skill in `~/.ryter/skills` whose `template.md` set the page's title, sections and last line:
- Asked for "release notes for this project", the model loaded the skill, then read `template.md` through `load_skill`, then loaded `canvas`.
- It showed a page that followed the template exactly.
- The saved page begins with the doctype and the lock.
- The model told the user the sandbox kept the page from opening.
- Nothing was written into the project.
