# Ryter product gap analysis

Assessment date: 2026-10-29  
Baseline: version **0.42.0**, branch `dev`, commit `b3d01dae200d827c907005d33f8c228ad3a9c6e7`  
Scope: the checked-out product, its documented promises, implementation, tests, packaging, and readiness criteria.

## Executive assessment

Ryter has a substantial working product: one conversation, four hats, per-hat model routing, provider integration, permission enforcement, checkpoints, audit and repair, project commands, session recovery, cost accounting, MCP, and signed installation/update machinery. The local automated checks run for this analysis passed. The largest remaining gaps concern the strength of its guarantees and the evidence supporting them, rather than an absence of core features.

The highest-priority work is to:

1. Prevent audit rollback from overwriting concurrent human edits.
2. Make routing changes atomic so displayed routing policy and the active provider cannot diverge on failure.
3. Prevent large roadmaps from crowding decisions and notes out of project memory.
4. Bound MCP input and connection resources.
5. Complete real provider and platform validation, with retained evidence.

Budget limits are request-boundary stops, not guaranteed maximum bills. Audit checkpoints restore repository files, not arbitrary application state. These distinctions should be visible where users make decisions, not only discoverable in detailed documentation.

This analysis does **not** certify that the product is free of security or data-loss defects, and does not propose a release or version change. The existing user-owned 1.0 gate remains the definition of readiness.

## Method and evidence boundaries

Reviewed the README, current guide, roadmap, configuration, release workflows, benchmark methodology and published results; inspected the agent loop, permission/sandbox boundaries, persistence, Git recovery, provider routing and streaming, context/memory handling, MCP transports, project-command discovery, and TUI verification surfaces. Historical design and gap documents were treated as archives, not current specifications.

Findings use three evidence labels:

- **Confirmed implementation:** behavior follows directly from the current implementation. Where no focused reproduction was run, that is stated; passing existing tests is not a reproduction of a newly identified defect.
- **Documented limitation:** current documentation or roadmap explicitly acknowledges the restriction, corroborated in code where practical.
- **Validation gap:** required evidence was not found in the reviewed repository, or a relevant check remains manual/ignored. This does not prove the feature fails or that no external evidence exists.

No provider credentials were read, no paid inference was run, and no live provider/model/pricing claims were independently checked. Published benchmark results are assessed as repository evidence, not independently repeated measurements. No external competitor research was performed. Recommendations below concern this implementation and its stated contract.

## Existing strengths to preserve

- The four-hat workflow and headless interface exist; the missing work is not to rebuild the removed crew architecture.
- Unknown and incomplete spend are represented honestly. Incomplete accounting blocks further calls under a configured budget, including after resume. Previously reported unlimited repeated calls to an unpriced model are no longer an accurate diagnosis.
- Session files use locking, private creation, atomic writes and torn-tail recovery. A blanket claim that persistence has no corruption recovery would be wrong.
- Provider parsing has fixtures and adversarial streaming tests; HTTP retries, deadlines and cancellation exist. The remaining provider gap is provenance and live compatibility coverage.
- Sandbox profiles fail closed when requested. Active-session notes/pages are scoped, and Ryter's own bookkeeping runs outside tool scopes. An old roadmap item still asking for session scoping is stale.
- Installer and updater signature verification, dependency policy checks, license notices, Linux/macOS CI, benchmark hidden tests and negative controls already exist.
- The TUI has golden layouts and direct style assertions. The archived claim that all styling is untestable is no longer generally true.

## Detailed findings

### G01 — Audit rollback can erase concurrent human work

**Evidence:** [agent.rs](../../crates/ryter-core/src/agent.rs), `audit_checkpoint`, `audit_restore`, `audit_done`; [git.rs](../../crates/ryter-core/src/git.rs), `paths_between`, `restore_paths`.

The audit snapshots the tree before running, snapshots it afterward, and restores differing paths other than the retained `.ryter/` paths. That comparison identifies changed content, not who changed it. A developer editing a source file while an audit is running can therefore have that edit restored to the earlier checkpoint even if the audit never touched the file. An unrelated new file can likewise be included in the rollback.

This is established by the restore algorithm; a concurrent-editor runtime reproduction was not performed. Build undo has separate protections and should not be assumed to make the audit path safe.

**Close when:** a deterministic test changes an unrelated file during an audit and preserves it; an edit to the same path produces a recoverable conflict rather than silently replacing the user's version. Record provenance where possible, preserve both versions where ownership is ambiguous, and make recovery available. Any change in execution isolation must respect the existing product direction.

### G02 — A routing change can be saved without becoming effective

**Evidence:** [worker.rs](../../crates/ryter-tui/src/run/worker.rs), `Work::SetRouting` around line 788; [ROADMAP.md](../../ROADMAP.md), 0.42.0 open review findings.

The worker changes its configuration and the agent's configuration before resolving the credential needed to rebuild the current provider. If credential resolution fails, it emits an error but leaves the existing provider object in place. The next call can still use its old routing rules while configuration records the new ones. This matters especially for host restrictions, retention preferences, and price constraints.

The error path is confirmed in code and acknowledged by the roadmap; no credential-store failure was induced in this session.

**Close when:** provider/configuration changes commit together, or the connection becomes explicitly unavailable until the new policy can be applied. A failed rebuild must never permit a subsequent call under obsolete rules while presenting the new policy as effective. Test failures on both current and alternate hat/scout connections.

### G03 — A large roadmap excludes decisions and notes from memory

**Evidence:** [memory.rs](../../crates/ryter-core/src/memory.rs), `MEMORY_CAP`, `load_project_memory`, `append_file`; [prompt.rs](../../crates/ryter-core/src/prompt.rs), project-memory injection; [project_file.rs](../../crates/ryter-core/src/project_file.rs), bounded prefix reads.

The shared memory budget is 48,000 bytes. Files are appended in order: `ROADMAP.md`, `DECISIONS.md`, then notes. A sufficiently large roadmap fills the allocation and leaves no room even for the decisions header. This checkout already has a 100,726-byte roadmap and a 424,065-byte decisions file. The algorithm consequently gives the roadmap the available budget and omits the root decisions file and notes.

This is a source-and-size finding, not a live model experiment. The separate `.ryter/decisions.md` injection does not substitute for the root `DECISIONS.md` promised by project memory. Safe UTF-8 truncation exists; the defect is allocation and omission visibility.

**Close when:** each memory source receives a deliberate budget, active roadmap sections take precedence over historical Done entries, and omitted sources are identified. Test oversized roadmap/decisions/notes together, including multibyte text. A section index or bounded summaries can solve this without adding a database.

### G04 — MCP resource limits do not cover transport input

**Evidence:** [mcp/server.rs](../../crates/ryter-core/src/mcp/server.rs), `serve_session` around line 295; [mcp/client.rs](../../crates/ryter-core/src/mcp/client.rs), stdout reader around line 141; [mcp/listen.rs](../../crates/ryter-core/src/mcp/listen.rs), listener loops.

Inbound processing limits pending work and queues 64 lines, but each line is read with `BufRead::lines()` without a byte ceiling. A peer can supply an arbitrarily large unterminated frame before authentication completes. Listener loops spawn a thread per connection without an evident connection cap or initialization deadline. Outbound stdout also reads unbounded lines and uses an unbounded channel; a faulty server can flood it independently of the tool-call timeout.

These are code-confirmed resource-exhaustion risks; no stress or exploitation test was run. Authorized use of a local server lowers exposure but does not remove accidental failure modes. TCP also uses plain sockets; the documented token is authentication, not transport encryption.

**Close when:** inbound/outbound frame bytes, queued bytes, connection counts and initialization time are bounded. Oversized frames and flooding servers must fail with a useful diagnostic while cancellation/status remain responsive. Document TCP as a local/trusted transport or require an encrypted channel for remote use; do not imply full standard HTTP MCP compatibility.

### G05 — Provider fixtures lack a complete live compatibility evidence trail

**Evidence:** [fixtures](../../crates/ryter-core/fixtures/), [llm/parse.rs](../../crates/ryter-core/src/llm/parse.rs), [llm/http.rs](../../crates/ryter-core/src/llm/http.rs), [scripts/acceptance.py](../../scripts/acceptance.py), [ROADMAP.md](../../ROADMAP.md), item 7.

There is meaningful coverage of three wire formats, parallel calls and streaming errors. The offline CLI fixture primarily exercises a synthetic Chat Completions service. The roadmap still requests recorded provider wire fixtures and a hand-run tool round trip per built-in provider before release. The ignored live test lists models; that is not an end-to-end tool execution check.

**Close when:** retain sanitized, dated captures with provider/backend and expected outcomes; replay tool calls, parallel calls, truncation, cancellation and accounting. Record one explicitly budgeted live tool round trip per built-in provider before a release. Keep routine CI offline and record local-model compatibility separately. Do not infer working tool calls from successful model listing.

### G06 — Platform support is broader than completed human acceptance

**Evidence:** [README.md](../../README.md), install section; [ROADMAP.md](../../ROADMAP.md), Now/Next; [ci.yml](../../.github/workflows/ci.yml); [release.yml](../../.github/workflows/release.yml).

Linux's setup and real-project flow have recorded user acceptance. macOS CI and release builds exist, but the roadmap still owes a human install/key/change/TUI pass, real clipboard testing, and macOS sudo interaction. WSL2 is the advertised Windows route and is explicitly untried. Its terminal behavior and kernel sandbox enforcement are not established by Linux CI.

The Linux-only benchmark and Landlock implementation are deliberate restrictions, not missing native macOS implementations that must automatically be added. Native Windows is explicitly deferred.

**Close when:** retain an install → key → model → edit → test → audit → undo → resume record on macOS and WSL2, including three terminal widths, Unicode/paste/selection and unsupported sandbox diagnostics. Separate built, automated-tested, and human-tested platforms in the support table. A macOS elevated-command check must be performed by the user, not by an agent attempting real sudo authentication.

### G07 — A session budget is not a strict maximum charge

**Evidence:** [agent.rs](../../crates/ryter-core/src/agent.rs), `over_budget`, `admit_request`, accounting after completion; [guide.md](../../docs/guide.md), Spend; [README.md](../../README.md), budget description.

Admission compares spending already recorded with the cap. It does not reserve a conservative cost for the next request. A final request may exceed the remaining allowance. A previously unseen unpriced model is allowed one request and then blocked if it remains unpriced. Incomplete accounting correctly blocks further calls; that protection should be preserved.

The README's wording that `/budget 5` “caps the session” can imply a tighter guarantee than this implements. The guide explains unknown prices but should explain request overshoot equally directly.

**Close when:** call it a request-boundary spending limit in the UI/guide, disclose remaining-call exposure, and decide whether stricter admission is required. Strict mode would need output-token limits, conservative input/cache pricing, treatment of provider-only charges, and a policy for unknown prices. Test a cap smaller than the next request and label any unavoidable estimation error.

### G08 — Audit rollback cannot restore all application side effects

**Evidence:** [git.rs](../../crates/ryter-core/src/git.rs), checkpoint excludes ignored files; [agent.rs](../../crates/ryter-core/src/agent.rs), audit lifecycle; [guide.md](../../docs/guide.md), ignored-file undo and sandbox restrictions; [README.md](../../README.md), audit description.

The audit runs builds/tests and starts the product behind repository checkpoints. Those checkpoints do not restore ignored database files, container volumes, external services, or arbitrary shell effects. Direct model writes to ignored files have separate build undo support, but shell writes are explicitly excluded. “A checkpoint puts back anything it changed” in the README is therefore broader than the guarantee.

**Close when:** describe the rollback boundary on the audit approval surface and in introductory documentation. Run destructive checks against disposable application data or explicit user-selected fixtures. A regression should demonstrate that a changed ignored database is reported as outside recovery coverage rather than implying it was restored. Keep this separate from G01's concurrent-editor issue.

### G09 — Elevated commands have a known policy coverage gap

**Evidence:** [ROADMAP.md](../../ROADMAP.md), Next, elevated command review notes; [tools/policy.rs](../../crates/ryter-core/src/tools/policy.rs), root command classification; [guide.md](../../docs/guide.md), sudo limitations.

The roadmap acknowledges that root programs able to execute their own text are refused by known names, while unlisted interpreters or shell escapes can evade that classification. It also acknowledges directory-listing exposure when a privileged listing names an ancestor of protected folders. Approval is meaningful, but it does not make these boundaries complete.

**Close when:** decide the supported privileged-command contract with the user, then implement it with explicit program/argument capabilities or a deliberately narrow allowlist. Include interpreter aliases, client shell escapes and ancestor traversal in non-authenticating fixtures. This analysis did not attempt sudo authentication or reproduce a privileged bypass.

### G10 — Sandbox coverage is optional and narrower than general containment

**Evidence:** [sandbox.rs](../../crates/ryter-core/src/sandbox.rs), `SandboxProfile` and `apply_linux`; [guide.md](../../docs/guide.md), Doctor and sandbox; [ROADMAP.md](../../ROADMAP.md), Next.

The default is `off`. Enabled profiles constrain filesystem access but not network access; Docker access can escape the filesystem boundary; outbound MCP servers have their own permissions; rootless Podman is incompatible. Home restrictions can also break legitimate first-run tool configuration. Older kernels lack signal scoping even when other restrictions hold.

**Close when:** provide a concise capability summary in setup/doctor for the active configuration: filesystem, network, processes, containers, MCP and unsupported features. Resolve the profile-versus-toolchain usability question before considering default-on. Add profile compatibility fixtures for normal builds. Network containment or macOS sandbox parity is a separate product decision, not a prerequisite inferred by this report.

### G11 — Mixed-language projects receive incomplete automatic commands

**Evidence:** [verbs.rs](../../crates/ryter-core/src/verbs.rs), `detect` around line 1476; [ROADMAP.md](../../ROADMAP.md), 0.41.0 open findings.

A root `Cargo.toml` returns Rust commands immediately, before checking `package.json`. A Rust backend plus frontend can therefore receive a plausible test/check configuration that omits the frontend. Nested project discovery is also limited by root-manifest detection. Explicit run files can work around this; narrow-test results already disclose limited coverage.

**Close when:** discover all relevant ecosystems, present their scope for approval, and preserve explicit user commands. Test mixed manifests, nested packages and workspaces. Display exactly what a “whole suite” covers when the configured run file is incomplete.

### G12 — Unknown-model context fallback can over-admit requests

**Evidence:** [compact.rs](../../crates/ryter-core/src/compact.rs), `window_for`, `ensure_fits`; [agent.rs](../../crates/ryter-core/src/agent.rs), `window_for_seat`; [config.rs](../../crates/ryter-core/src/config.rs), `context_windows`.

When neither override nor available model metadata supplies a window, unknown models fall back to 200,000 tokens. A local server with a much smaller configured window can reject requests admitted by that estimate. Token estimation is also bytes/4 rather than the actual tokenizer. Existing overrides and preflight checks mitigate this but require correct metadata or user intervention.

**Close when:** distinguish verified, configured and assumed limits in setup/context displays; require or propose a conservative window for unknown local models. Test a small-window server and model changes near capacity. Validate boundary behavior with representative Unicode, source and tool schemas. This report does not assert any current provider's actual window size.

### G13 — Compaction preserves enough prose to reach a hard floor

**Evidence:** [compact.rs](../../crates/ryter-core/src/compact.rs), `compact`, `extract_prefix`, `ensure_fits`.

Compaction drops/shortens tool material but keeps earlier user messages and assistant notes verbatim in a prefix. This protects instructions from an invented summary, but long conversations dominated by prose may shrink little. Admission then refuses the request and recommends a new session or larger window. This is a safe failure, but a continuity gap for sustained work.

**Close when:** document the floor and provide an explicit, inspectable handoff artifact retaining current objective, constraints, accepted decisions and unfinished work. Test a long prose-only conversation and a resume after compaction. Any semantic summary should be user-visible; silently dropping constraints is not an acceptable fix.

### G14 — Routing configuration still has discoverability and classification defects

**Evidence:** [config.rs](../../crates/ryter-core/src/config.rs), `ConnectionConfig::is_openrouter`; [ROADMAP.md](../../ROADMAP.md), 0.42.0 open review findings; [panel/routing.rs](../../crates/ryter-tui/src/panel/routing.rs).

`is_openrouter` uses a substring search on the entire base URL. A hostname such as `openrouter.ai.example.invalid`, or the string in a path, satisfies that check even though the host is not OpenRouter. This is confirmed misclassification, not proof that Ryter automatically sends credentials to an attacker: users still configure the endpoint.

The roadmap separately records missing `:floor`/`:nitro` picker selection, no routing display in `ryter connections`, confusing first use, and edge cases in empty percentile and project override tables.

**Close when:** parse and compare normalized hosts, cover misleading host/path examples, display the effective routing policy and its source, and make CLI/TUI inspection consistent. Test override precedence and clearing. Address G02 first, because correctness of effective policy precedes form polish.

### G15 — Real-session gate replay is not a routine regression gate

**Evidence:** [tools/policy.rs](../../crates/ryter-core/src/tools/policy.rs), `replay_live_session_asks_through_the_gate` around line 12007; [ci.yml](../../.github/workflows/ci.yml); [ROADMAP.md](../../ROADMAP.md), item 2.

The kept replay harness requested by an older roadmap entry now exists. It is ignored and requires a recording at `tests/fixtures/gate-replay/events.jsonl`; it did not run in this assessment. The remaining gap is representative, sanitized replay data and repeatable assertions, not absence of a harness.

**Close when:** preserve a small deterministic corpus of real command patterns with expected decisions, including both legitimate builds and destructive actions. Run that corpus on policy changes. Track unnecessary approval prompts and missed required prompts separately, then confirm with a new real session. Broadening permissions simply to lower prompt counts would miss the safety objective.

### G16 — Benchmark evidence is narrow relative to the product promise

**Evidence:** [bench/README.md](../../bench/README.md), [published comparisons](../../docs/bench/README.md), [Opus comparison](../../docs/bench/2026-10-22-opus-5-5.md), [README.md](../../README.md).

The published comparisons cover ten small tasks and primarily the build hat, not the full plan/build/audit/repair/scribe experience. The methodology openly distinguishes estimated subscription costs from API charges and says tools use their installed configuration. Those disclosures are strengths, but they limit generalization. Ten tasks also make one task a ten-percentage-point solve-rate change.

Hard tasks and reference validation already exist; their existence does not establish repeatable live hard-task results. Some repeat-run artifacts are described as remaining in an ignored local `target/` directory.

**Close when:** publish sanitized per-task artifacts with configuration, commit, model route, accounting provenance, time and repeated-run variability. Add hard tasks and real-project workflow cases measuring audit misses, repair success and human intervention. Keep headline claims scoped to measured tasks. No new paid benchmark is authorized by this analysis.

### G17 — Stored sessions and Git checkpoints need an explicit lifecycle

**Evidence:** [session.rs](../../crates/ryter-core/src/session.rs), `Session::remove`; [git.rs](../../crates/ryter-core/src/git.rs), `checkpoint`; [trace.rs](../../crates/ryter-core/src/trace.rs); [guide.md](../../docs/guide.md), Sessions.

Diagnostic log rotation exists. Sessions and their pages can be deleted. Git checkpoint objects are retained by `refs/ryter/undo/...`; session deletion does not remove those refs, and no checkpoint-pruning path was found in the inspected code. Repository objects can retain old source content and grow over time even after a conversation is removed.

The guide describes storage locations, but not a complete retention, export, deletion and recovery contract spanning session files, recovery backups, project spend aggregates and repository checkpoints. Deleting a session should not silently be presented as erasing every trace or preserving every historical total without defining that behavior.

**Close when:** document what persists and why; offer size/age visibility and an explicit cleanup preview. Preserve active undo/recovery references and user branches. Test session deletion and checkpoint cleanup separately. Cleanup must be opt-in and explain the loss of recovery history.

### G18 — TUI automation does not complete terminal or accessibility acceptance

**Evidence:** [tui/tests.rs](../../crates/ryter-tui/src/tests.rs), [draw.rs](../../crates/ryter-tui/src/draw.rs), [ROADMAP.md](../../ROADMAP.md), selection/light-theme notes.

Layout and style tests exist, but the roadmap still calls for real drag-and-paste on Linux/macOS, a light-theme contrast pass, and resolution of selection edge cases. Scripted mouse reports and fake clipboard tools cannot validate terminal integration. No complete screen-reader/reduced-motion acceptance record was found in the reviewed documentation; this is missing evidence, not a claim that every such user is blocked.

**Close when:** record keyboard-only approval/cancel flows, real clipboard use, Unicode and wrapped-copy behavior, narrow-screen resize, visible focus, light/dark/16-color/NO_COLOR contrast, and reduced-motion/screen-reader results. Prioritize approval and cancellation surfaces over decorative polish. Fix the documented selection errors with targeted regressions.

### G19 — Distribution validation and recovery procedures need completion

**Evidence:** [release.yml](../../.github/workflows/release.yml), [ci.yml](../../.github/workflows/ci.yml), [install.sh](../../install.sh), [update.rs](../../crates/ryter-core/src/update.rs), [guide.md](../../docs/guide.md).

Four binary targets are built. Most artifact smoke tests only execute `--version`; the Intel macOS cross-build is not executed in that release job. Main CI provides stronger Linux/macOS coverage, but not the full installed-artifact journey on every target. A signed checksum authenticates an archive; it does not prove an installation is usable on a target machine.

The installer also depends on OpenSSL 3 with Ed25519 support. The prerequisite is documented, but first-run success on actual supported systems remains part of G06. A documented release-key rotation/revocation and failed-update recovery drill was not found in the reviewed material.

**Close when:** retain installed-artifact smoke results for the supported matrix, including a headless fixture turn and clean upgrade/recovery. Document the signing-key recovery/rotation procedure without exposing secrets. Dependency CI is valuable but the current advisory state was not refreshed in this analysis.

### G20 — Planning and user documentation have measurable drift

**Evidence:** [ROADMAP.md](../../ROADMAP.md), [guide.md](../../docs/guide.md), [deny.toml](../../deny.toml), [Cargo.toml](../../Cargo.toml), [gaps.md](../../gaps.md), [Opus comparison](../../docs/bench/2026-10-22-opus-5-5.md).

Examples in the current checkout:

- Next still asks to narrow session sandbox grants, while code and the guide already describe active-session isolation.
- Next asks for a kept gate replay test and CLI tests, while both now exist; what remains is coverage/data and execution.
- The dependency-maintenance guide says two ignored advisories, including `paste` through ratatui 0.29. The manifest uses ratatui 0.30 and `deny.toml` contains one advisory exception for `bincode`.
- The archived gap report still contains an open style-test claim that should not be imported into a current backlog.
- The Opus comparison says ten tasks include nine Python plus one Rust and one TypeScript; its listed standard tasks contain eight Python plus one of each.

**Close when:** reconcile each item with current evidence; clearly distinguish resolved implementation, remaining validation and historical context. Link readiness items to tests or manual records. Check current commands/config examples and benchmark task counts mechanically where feasible. Do not silently rewrite historical results.

### G21 — Large-project performance lacks a reproducible acceptance baseline

**Evidence:** [map.rs](../../crates/ryter-core/src/map.rs), [memory.rs](../../crates/ryter-core/src/memory.rs), [project.rs](../../crates/ryter-core/src/project.rs), [session.rs](../../crates/ryter-core/src/session.rs), TUI rendering tests, benchmark task scope.

The implementation has deliberate bounds, rendering tests and incremental project-spend aggregation. These should not be mistaken for evidence about a large monorepo or years of local history. No retained end-to-end baseline was found for startup, map creation, checkpoint time, session listing/resume and memory consumption at those scales. Memory starvation in G03 is one already observable scale failure.

**Close when:** create generated, deterministic fixtures for many files, large histories and large diffs; record median/tail latency and peak memory. Set acceptance thresholds after measuring representative machines. Test cancel responsiveness during slow operations. Keep measurement local and opt-in; hosted telemetry is unnecessary.

### G22 — Safety and state management are concentrated in large modules

**Evidence:** [agent.rs](../../crates/ryter-core/src/agent.rs) has 10,677 lines; [tools/policy.rs](../../crates/ryter-core/src/tools/policy.rs) has 14,174; [config.rs](../../crates/ryter-core/src/config.rs) has 4,204, including tests. Release history documents repeated review corrections around policy, routing and command parsing.

Line count alone is not a defect. Here it coincides with many interacting responsibilities and configuration copies. G02 illustrates the practical cost: a saved setting, worker config, agent config and constructed provider can diverge. Large shell-classification code also requires careful regression evidence when making apparently small changes.

**Close when:** extract focused state transitions and policy components incrementally, preserving behavior with existing and property-based fixtures. Prefer one explicit transaction for applying provider configuration. Establish invariants for hat changes, request admission, permission decisions and persistence. Avoid a broad rewrite while safety findings remain unresolved.

## Measures of completion

Use local reports or explicitly opted-in evaluation; no hosted telemetry is needed.

- **Safety:** zero lost concurrent edits in deterministic audit tests; zero post-failure calls under obsolete routing policy; bounded memory/threads under malformed MCP input.
- **Setup:** completed install/key/change/undo/resume checklist for each advertised platform, with machine/terminal details and no undocumented steps.
- **Providers:** every built-in backend has replay coverage and dated live tool-round-trip evidence; account/model-list success alone does not count.
- **Cost:** known request overshoot is disclosed and measured; unknown/incomplete spend remains visibly incomplete and blocks calls under the documented policy.
- **Gate quality:** unnecessary prompts per representative build and missed required prompts tracked separately; both outcomes need fixtures.
- **Workflow quality:** task completion, audit false passes, repair success, human interventions, elapsed time and total cost measured across the full flow.
- **Scale:** startup/resume/map/checkpoint and cancellation latency measured on deterministic large fixtures, with explicit budgets established from the baseline.
- **Documentation:** each open roadmap item names remaining work and current evidence; resolved implementation is not left as an undifferentiated open feature.

## Deliberately excluded expansion

Native Windows, additional hats, crew/delegation, more web-search providers, a hosted service, enterprise administration and new database infrastructure are not inferred prerequisites for the current product. Session search and richer MCP transport interoperability may be useful later, but should follow demonstrated demand. The immediate opportunity is to make the existing workflow's promises precise, enforceable and verifiable.
