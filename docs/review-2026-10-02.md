> **Archive.** Reviewed on 2026-10-02, against 0.11.0. The repair stages below
> landed. The test hat this plan tells you to exercise was removed on
> 2026-10-03, and the review hat is the audit hat. It is not a current work list.

Reviewed 2026-10-02, version 0.11.0, branch `dev`, commit `af9ec369386216af07020eaba5d01fe4d8a5a4ae`.

Ryter has a substantial regression suite and a clear separation between its core, terminal interface, and CLI. The ordinary checks pass. However, targeted tests reproduced 13 defects involving secret access, file preservation, recovery, provider streaming, spending, process cleanup, and MCP cancellation. Fix the security and data-preservation failures first, then verify the complete plan → build → review → test flow on a real project.

The findings and original validation below describe that initial commit. Subsequent repair implementations are indexed here; the historical probe failures are not a statement that the repaired branches still fail. No release or version bump is part of this work.

## Reproduced defects

P1 means a high-priority security, data-preservation, or spending-control defect. P2 means a correctness or reliability defect that should be scheduled after the P1 work. These are repair priorities, not release-version recommendations.

### 1 Untrusted project instructions can disclose linked secrets

**P1.** [prompt.rs](../crates/ryter-core/src/prompt.rs#L34), lines 34–43, and [memory.rs](../crates/ryter-core/src/memory.rs#L9), lines 9–32.

Instruction and memory loading calls `read_to_string` directly. A project can contain `RYTER.md`, `ROADMAP.md`, or another loaded memory path that is a symlink to a sensitive file. The target's contents enter the system prompt even when `trusted` is false, before any tool permission decision. With the default sandbox off, an untrusted checkout can therefore cause disclosure to the selected model provider.

**Reproduced:** symlinked `RYTER.md` and `ROADMAP.md` to a fixture `.env`; `prompt::system(..., false)` included `AUDIT_FAKE_SECRET=fixture-only`.

**Repair:** use a common safe project-file reader for instructions and memory, rejecting links or validating the resolved target and every directory component against the permitted root and secret policy. Bound the total prompt material read. Cover instruction fallback, memory files, and a symlinked `notes` directory.

### 2 Search bypasses the protection used by direct file reads

**P1.** [tools/fs.rs](../crates/ryter-core/src/tools/fs.rs#L291), lines 291–299.

The grep walker checks the displayed pathname for secrets, then reads that pathname. `path.is_file()` and `read_to_string()` follow a file symlink, but the loop does not authorize its resolved destination. Disabling directory-link traversal does not prevent this file-link case.

**Reproduced:** direct `read_file` of `innocent.txt → ../.env` was denied; `grep` over the same project returned the fake secret through `innocent.txt`.

**Repair:** authorize every resolved search result using the same boundary and secret checks as direct reads, or skip links. Test aliases to secrets inside and outside the project, linked roots, and all hats. Do not rely on `.gitignore` to protect secrets.

### 3 Nested environment files evade secret classification

**P1.** [tools/policy.rs](../crates/ryter-core/src/tools/policy.rs#L5738), lines 5738–5770.

The `.env.*` check uses `s.starts_with(".env")` on the entire relative path. It catches `.env.production` at the top level but misses `config/.env.production`. These files are common in projects with multiple applications or deployment environments.

**Reproduced:** `decide("read_file", {"path":"config/.env.production"}, review_context)` returned `Allow`.

**Repair:** classify the basename and protected path components separately. Keep the explicit example-file exceptions, and test nested `.env` variants, protected directories at the project root, public keys, tracked secrets, and symlink aliases across every reader.

### 4 A socket path can replace an ordinary file

**P1.** [mcp/listen.rs](../crates/ryter-core/src/mcp/listen.rs#L17), lines 17–34.

When connecting to an existing socket path fails, `bind_unix` unconditionally removes the path. It does not first require it to be a socket or distinguish a stale socket from another connection error. A mistaken `--socket` path can therefore destroy an existing file.

**Reproduced:** created `important.txt` containing fixture data and passed it to `bind_unix`; binding succeeded after replacing the file with a socket.

**Repair:** inspect with `symlink_metadata`; reject regular files, directories, and symlinks. Replace only a verified stale socket, and propagate permission-setting failures. Test regular files, live and stale sockets, symlinks, and permission failures.

### 5 Undo fails when Ryter starts below the repository root

**P1.** [git.rs](../crates/ryter-core/src/git.rs#L130), lines 130–145, and [agent.rs](../crates/ryter-core/src/agent.rs#L1892), the undo and redo paths.

Snapshot differences return repository-relative paths, but `restore_paths` applies them relative to the session's working directory. Starting Ryter in `repo/app` causes a returned path such as `app/file.txt` to be applied from `repo/app` again. Existing-file restoration errors; removal paths have the same inconsistent base.

**Reproduced:** checkpointed and changed `app/file.txt` from inside `app`; restore failed with `pathspec 'app/file.txt' did not match any file(s) known to git`.

**Repair:** establish one path convention for snapshots and recovery, using the repository root for repository-relative paths. Explicitly preserve the intended project scope. Test undo, redo, added and deleted files, ignored files, nested launch directories, and preservation of unrelated sibling-project work.

### 6 Parallel streamed tool calls lose their argument identity

**P2.** [llm/parse.rs](../crates/ryter-core/src/llm/parse.rs#L164), lines 164–181, and [llm/mod.rs](../crates/ryter-core/src/llm/mod.rs#L168), lines 168–180.

The Chat Completions parser discards each tool delta's `index`. The accumulator appends every fragment without an ID to the most recently created call. If two calls are introduced before their argument fragments arrive, fragments for the first call go into the second. Parallel calls are a supported provider behavior; OpenRouter documents them as enabled by default for most models. [OpenRouter tool-calling documentation](https://openrouter.ai/docs/guides/features/tool-calling#parallel-tool-calls).

**Reproduced:** calls `a` and `b`, followed by arguments for indexes 0 and 1, yielded empty arguments for `a` and two concatenated JSON objects for `b`.

**Repair:** preserve protocol-specific call identity through parsing and accumulation. Test interleaved fragments, multiple calls in one frame, missing IDs after the first frame, and truncation. A temporary mitigation is to request one tool call at a time where supported.

### 7 Commit-message drafting bypasses an exhausted budget

**P1.** [agent.rs](../crates/ryter-core/src/agent.rs#L2096), `draft_commit`, and [agent.rs](../crates/ryter-core/src/agent.rs#L2172), lines 2172–2189.

Normal turns check the session budget, but the `one_shot` path used to draft a commit message calls the provider without the same check. Repeated drafts can continue spending after normal work has stopped at the cap.

**Reproduced:** with both the session spend and cap set to $1, `draft_commit` returned a model-generated message instead of `Error::Budget`.

**Repair:** route every paid request through shared budget admission, including auxiliary requests. Reject at-cap and unresolved-unpriced requests before contacting the provider. Keep the user's ability to write a commit message manually.

### 8 Failed or cancelled streams discard already reported usage

**P1.** [agent.rs](../crates/ryter-core/src/agent.rs#L339), lines 339–405; the auxiliary request loop has the same early-return pattern.

Usage and cost accumulate in local variables and are recorded only after normal stream completion. A stream error or cancellation returns before recording them. Already reported spending disappears from the ledger and budget, allowing subsequent work to use an understated total.

**Reproduced:** a fake provider emitted usage for 1,000 input tokens, then an error. The turn failed and its spend log stayed empty.

**Repair:** finalize accounting on success, error, cancellation, and truncation. Preserve known provider usage; record an explicitly incomplete or unknown charge when final billing is unavailable. Do not claim exact charges for a cancelled request without provider evidence. Verify that resume preserves the accounting and budget state.

### 9 Partial price overrides silently make missing rates free

**P2.** [spend.rs](../crates/ryter-core/src/spend.rs#L229), lines 229–234, and the optional fields in `config::PriceOverride`.

An override replaces the whole rate row, defaulting absent input and output prices to zero. Supplying only an input price therefore makes output tokens free in Ryter's calculations, even though their price is unknown.

**Reproduced:** an input-only override for a fixture model priced 1,000 output tokens at `Some(0.0)`.

**Repair:** merge supplied fields with known catalog rates, or reject incomplete overrides where missing rates cannot be resolved. Validate prices as finite and nonnegative. Preserve explicit zero rates for intentionally free models.

### 10 A failed start leaves its child processes running

**P2.** [run.rs](../crates/ryter-core/src/run.rs#L554), lines 554–564.

The timeout and cancellation paths call `take_down`, but a nonzero exit from the start command returns immediately. If startup created a child or partially brought up a stack before failing, it remains running without a successful `Started` record.

**Reproduced:** `sleep 30 & echo $! > child.pid; exit 7` returned `Start::Failed` while its recorded child remained alive. The probe then terminated that child by its recorded PID.

**Repair:** make every unsuccessful startup exit account for processes and services it started. Apply the approved cleanup semantics, preserve a record if cleanup fails, and report what remains. Test nonzero exit, readiness timeout, cancellation, partial stack startup, and cleanup failure.

### 11 Run-file normalization changes the meaning of commands

**P2.** [run.rs](../crates/ryter-core/src/run.rs#L78), lines 78–88.

`RunFile::tidy` splits each command on all whitespace and rejoins it. This changes spaces inside quoted strings and removes meaningful newlines. File paths, arguments, and multiline commands can become different commands after loading or proposing the run file.

**Reproduced:** `printf '%s' 'a  b'` became `printf '%s' 'a b'`.

**Repair:** preserve command bytes apart from any explicitly permitted outer trimming. Treat display formatting separately from execution. Verify quoted whitespace, multiline TOML, line continuations, and any supported here-documents through save, approval, reload, and execution.

### 12 MCP status requests can prevent cancellation

**P2.** [mcp/server.rs](../crates/ryter-core/src/mcp/server.rs#L333), lines 333–345, and [CLI main.rs](../crates/ryter-cli/src/main.rs#L658), lines 658–681.

While a prompt runs on a helper thread, the connection thread synchronously handles additional requests. The CLI host holds the agent mutex throughout the prompt, while `status` and `spend` acquire the same mutex. A status request blocks the connection thread, so a later cancellation request on that connection cannot be processed until the prompt finishes. A second prompt also enters synchronous dispatch.

**Reproduced:** a host with the CLI's locking behavior received prompt → status → cancel; cancellation was not handled until the test independently released the prompt. This probe uses the real MCP session dispatcher, with a controlled host instead of a paid provider.

**Repair:** serve status and spend from independent snapshots, and queue or reject another prompt without blocking request handling. Test cancellation while status, spend, a second prompt, and disconnect arrive during active work.

### 13 An interrupted transcript append makes a session unreadable

**P2.** [session.rs](../crates/ryter-core/src/session.rs#L668), lines 668–680.

The JSONL reader rejects the entire session when any line fails to parse. A process interruption during the last append can leave a valid history followed by an incomplete final record; resuming then fails rather than recovering the valid prefix.

**Reproduced:** created a session with a valid user message, appended an unfinished assistant JSON record, and reopened it. `Session::open` returned an EOF parse error.

**Repair:** recover a torn final record while preserving the original file and warning the user. Continue to treat corruption in the middle as a distinct error requiring deliberate recovery. Reconcile spend metadata and log records after interruption, and test both conversation files.

## Additional gaps

These are source-supported limitations and areas requiring further validation. They are separate from the 13 reproduced defects.

1. **Context limits do not follow the active hat's model.** `Agent::context_report` uses `self.model` and one window override, while requests use `hat_stack`. This limitation is already acknowledged in `ROADMAP.md` and `DECISIONS.md`. Compaction also returns unchanged when there are four or fewer user messages, regardless of how much tool output a long turn accumulated. Use the active route's actual limits, include tool schemas and output headroom, and compact within long turns. Require demonstrable reduction or an actionable stop before sending an oversized request. Preserve the user's constraints and unresolved work in the summary; the current extract principally retains tool and file names.

2. **Output limits apply after unbounded buffering.** [tools/shell.rs](../crates/ryter-core/src/tools/shell.rs#L369) accumulates stdout and stderr in growing vectors; the 32 KB tool-result cap applies afterwards. File readers and search also load complete files before reducing output. A noisy command or large file can exhaust memory despite the output cap. Use bounded head/tail buffers or bounded spooling, stream file ranges, and cap aggregate prompt memory. This review did not deliberately exhaust system memory.

3. **Sandbox session isolation is broader than the active project.** [sandbox.rs](../crates/ryter-core/src/sandbox.rs#L441) grants entire `sessions` and `pages` directories. The roadmap already calls out access to other projects' sessions. Narrow grants to the active session/project. Keep the existing documentation that filesystem sandboxing does not make access to a container daemon fully isolated; the default-off policy is a deliberate choice, not a newly discovered bug.

4. **Lifecycle state needs a truthful failure state.** [agent.rs](../crates/ryter-core/src/agent.rs#L1482) forgets the running-product record even when stopping fails. Readiness accepts any HTTP status below 500, and HTTPS checks only whether a TCP listener exists. Define how readiness proves this product is healthy, detect an existing unrelated listener, and retain failed-stop records so the user can retry. These paths were source-reviewed, not tested against real containers in this review.

5. **End-to-end acceptance coverage is incomplete.** The TUI has useful geometry and snapshot tests, with some explicit color assertions, but those do not validate a complete interactive work session. The CLI has one committed integration test. The ten benchmark tasks have no runner following crew removal, as `bench/README.md` states. Add repeatable hat-flow acceptance tests, error-path CLI coverage, and sanitized provider wire recordings. Keep optional paid live checks separate, using credentials explicitly supplied for that purpose. A successful real-project acceptance run is still needed before agreeing the product's completion criteria.

6. **Installation and maintenance have coverage gaps.** The updater verifies a release signature, but [install.sh](../install.sh#L60) verifies only a checksum downloaded from the same source. Bring bootstrap artifact verification into line with the signed updater, and test it with tampered local fixtures. Add a dependency-advisory and license check using an available free workflow or an explicit local tool setup. No vulnerable dependency is asserted by this review.

7. **Some integration and documentation promises exceed the implementation.** The MCP transcript resource returns a session ID rather than a transcript (`mcp/server.rs:122`). The README shows bare `ryter serve --socket`, but clap declares the option as requiring a path. The guide's safety section broadly says commands that change things ask, whereas build toolchains and project container commands can run without a question. Reconcile public commands, safety descriptions, the four hats, and incomplete integrations. Keep historical documents clearly labeled.

8. **The most sensitive code is difficult to reason about as a whole.** `tools/policy.rs` is about 8,900 lines and `agent.rs` about 6,200, including tests. Extract shell parsing, path authorization, request accounting, and lifecycle state into focused components after the behavior is covered. A broad refactor before the regression fixes would make the fixes harder to review. Add concurrency tests for simultaneous snapshots and session access; fixed private-index and temporary-file names deserve explicit ownership rules.

## Repair sequence

Each patch should introduce the relevant failing case into the maintained test suite, implement the fix, and pass the full workspace build, tests, clippy, and formatting checks. Keep the existing release number during repair work. The work below does not require reintroducing crew mode or a new orchestration system.

| Order | Proposed patch branches | Scope | Completion criterion |
| --- | --- | --- | --- |
| 1 | `file-read-boundaries-patch` | Defects 1–3 | No instruction, memory, search, or direct-read path exposes the fake protected files; every hat and alias form is covered |
| 2 | `socket-path-safety-patch`, `undo-root-paths-patch` | Defects 4–5 | Socket setup preserves non-sockets; undo and redo restore the intended files from nested launch directories while preserving unrelated work |
| 3 | `spending-integrity-patch` | Defects 7–9 | Every model request respects the budget; interrupted calls retain known usage; absent rates remain unknown or configuration is rejected |
| 4 | `streamed-tool-identity-patch` | Defect 6 | Multiple interleaved calls reconstruct their exact individual JSON arguments on supported protocols |
| 5 | `project-lifecycle-patch` | Defects 10–11 and lifecycle gap | Commands survive round trips unchanged; startup failure cleans up or records what remains; failed stops remain retryable |
| 6 | `mcp-responsiveness-patch`, `session-recovery-patch` | Defects 12–13 | Cancellation stays responsive during requests; a torn final record does not destroy access to valid history |
| 7 | `context-limits-patch`, `bounded-output-patch`, `sandbox-session-scope-patch` | Context, memory, and sandbox gaps | Long turns fit the active model or stop clearly; output memory stays bounded; another session is outside the sandbox grant |
| 8 | `hat-acceptance-patch`, `installer-verification-patch`, documentation updates | Product acceptance, provider recordings, install parity, public guidance | Repeatable full work flow, current command examples, tamper rejection, and a measured hats benchmark |

Stages 1–3 are the first repair milestone. Stages 4–6 complete the reproduced reliability failures. Stage 7 addresses limits that are likely to emerge in longer sessions. Stage 8 supplies evidence that the repaired components work together and that the guide matches the product.

The final acceptance scenario should start from an isolated project, approve a plan, make a change, run a review on the chosen model, use the Test hat with an approved run file, bring its report back, exercise undo and redo, restart the session, and verify cost and commit receipts. Include a nested repository directory, an interrupted model stream, a failed application start, a budget stop, and a user edit made after the agent's turn. Successful application instances should stay available for the user's own testing, with their addresses and fixture logins documented.

The benchmark should measure completed tasks, false review/test passes, reproducible failures, and recorded cost. Reuse the existing task fixtures where appropriate; validate their reference solutions before relying on their results. After the real-project acceptance run, agree the missing completion criteria with the user. This review makes no release or version-bump recommendation.
